# v2.2 Execution Plan — Email digest (subscribe → daily brief → weekly recap)

## Problem
The ranking engine and reader surface are mature, but there is **no habit/
retention loop**: a "finishable, read-every-morning" brief that lives on a
website nobody is pushed to. Distribution today is a GitHub Issue + optional
Telegram — both weak fits for the target persona (AI platform engineers do
morning triage in email/Slack). Email is the missing channel, and it is the
natural *push* vehicle for the memory moat (storylines + weekly "what you
missed" + knowledge-map updates).

See `docs/product-specs/email-digest.md` for the product spec.

## Guiding constraints
- **No subscriber PII in git** (public repo, no DB) → a newsletter provider
  (Buttondown or Resend) owns the list, double-opt-in, unsubscribe, compliance.
  We hold only an API key in env/secrets.
- **No LLM** — fully deterministic, reusing committed artifacts and the existing
  `publish_telegram.py` item helpers.
- **No hourly email** — sends on its own daily/weekly schedule; the hourly
  pipeline is untouched.
- **No topic personalization** — cadence preference only (anti-filter-bubble).
- **Secrets-gated no-op** — every step must no-op cleanly when keys are absent,
  like Telegram/PostHog.

## Phases (priority order — value first)

### Phase 1 — Acquisition (zero code)
- Set `DIGEST_EMAIL_SIGNUP_URL` (already read by `api/client-config.js`) to a
  provider-hosted signup form → the subscribe CTA lights up site-wide.
- Outcome: start building the list immediately, before any send code exists.

### Phase 2 — Daily brief send (core value) — DONE 2026-06-20
- `publish/publish_email.py`, mirroring `publish/publish_telegram.py`:
  - inputs: `data/processed/latest.json` (+ `data/digest/<date>.md`);
  - reuse `signal_label` / `short_why` / hype + Reader-boosted badges;
  - render email-safe HTML; call the provider **broadcast** API;
  - `--dry-run` prints HTML and never sends; missing `EMAIL_API_KEY` ⇒ no-op.
- Send cursor `data/email/state.json` (new committed runtime state, mirrors
  `data/health/alerts_state.json`): `daily.last_sent_date` guards double-sends.
- `.github/workflows/email-digest.yml` — daily morning cron, secrets-gated;
  commits the bumped cursor after a successful send.
- Links carry `?utm_source=email` for CTR attribution.
- Email layout: subject (item count + ~mins + top headline) → ranked top ~12 →
  **Continuing threads (1–3)** (Phase 3) → `✅ You're caught up` → footer.

### Phase 3 — Storyline deltas in the email ("Continuing threads") — DONE 2026-06-20
- Delta read of `data/storylines/index.json` against the cursor:
  qualify a thread when `last_updated > storylines.sent_through` **and** it has
  `member_sids` not in `seen_sids`.
- Copy from the narrative sidecar `editorial.whats_new`; fall back to
  `latest_title`. **Narration-lag guard:** if `covers_last_updated` is older than
  the thread `last_updated`, fall back to `latest_title` or hold for next send.
- Daily: cap 1–3; weekly: full set. Link `/storyline/<slug>`.
- Bump `storylines.sent_through` + extend `seen_sids` on success.
- **Trap:** diff on `last_updated`, never `generated_at` (the 5-hourly rebuild
  bumps `generated_at` every run — would mark every thread "new"). See
  `api/updates.js` for the established content-based-signal pattern.

### Phase 4 — Weekly recap send (the moat) — DONE 2026-06-20
- Friday cron (`0 23 * * 5`) in `email-digest.yml`; the run step maps that
  schedule to `--kind weekly` via `github.event.schedule`. `weekly.last_sent_week`
  is the idempotency guard.
- Inputs: newest `data/weekly/<week>.json` (by `end`) → title, intro (first 2
  paras), highlights, and themed categories (top `articles_per_category` each,
  linked to `/story/<sid>`).
- **Storylines that moved this week** and **New in the knowledge map** are
  **window-based**, not cursor-based: `storylines_in_window` / `wiki_in_window`
  select threads (`last_updated`) and wiki nodes (`updated`) inside the recap's
  `[start, end]`. *Why the deviation from the original cursor plan:* the daily
  send advances the shared `storylines` cursor every day, which would **starve**
  a cursor-based weekly by Friday. Windowing also matches the recap's own period
  and lets a thread legitimately appear in both a daily ("new today") and the
  Friday roundup ("what happened this week") — intended, not a bug. Consequently
  the weekly cursor stores **only** `last_sent_week`; no `wiki.sent_through` /
  `seen_slugs` are needed (the original schema's wiki cursor is dropped).
- Knowledge map is **weekly-only** (slow-moving, evergreen — would dilute the
  daily brief's finishability), `/topic/<slug>` links, node `updated` not the
  index `generated_at`.

### Phase 5 — In-page subscribe — DONE 2026-06-20  (provider: Resend)
- `api/subscribe.js`: POST `{ email, hp }` → Resend audience contact. Key read
  server-side only (never reaches the browser); honeypot + email validation;
  409/422 (already a contact) treated as idempotent success; 503 `not_configured`
  when creds absent. No `vercel.json` rewrite needed — `/api/subscribe` is
  filesystem-routed; added a `functions` entry excluding `data/**`.
- `api/client-config.js`: new `digest.email_subscribe_enabled` flag (true when
  `EMAIL_API_KEY` + `EMAIL_AUDIENCE_ID` are present on the deploy).
- `web/index.html`: the 🔔 subscribe menu renders an **in-page email form**
  (single opt-in, honeypot, PostHog `subscribe_email`) when
  `email_subscribe_enabled` and no external `DIGEST_EMAIL_SIGNUP_URL` is set;
  otherwise the prior external-link behavior is unchanged.
- **Single opt-in:** Resend adds the contact directly and its broadcasts carry
  the unsubscribe link + honor the `unsubscribed` flag. A double-opt-in
  confirmation step is a possible follow-up (send a confirm email before the
  contact goes live) — deferred.
- **Cadence preference deferred:** one audience = daily + weekly. Per-reader
  cadence (and definitely not topic segmentation) is a later, optional add to
  avoid half-built filtering.

## Validation
- `python3 publish/publish_email.py --dry-run` renders daily + weekly from the
  live tree without sending.
- Cursor round-trip: two runs on an unchanged tree ⇒ second emits no
  "Continuing threads" / "New in the knowledge map"; advancing one thread's
  `last_updated` ⇒ exactly that thread reappears.
- `node --check api/subscribe.js`; provider sandbox subscribe returns pending.
- Grep `run_full.sh` / hourly workflow ⇒ no email send wired in.
- Each phase ships independently and is secrets-gated, so an unconfigured prod
  stays a clean no-op.

## Rollback
- Phases 2–5 are additive and isolated. Unsetting `EMAIL_API_KEY` (or
  `config/email.yaml -> enabled: false`) reverts to no-send with zero pipeline
  impact. `data/email/state.json` is regenerated on next send if deleted. The
  subscribe CTA disappears when `DIGEST_EMAIL_SIGNUP_URL` is unset.

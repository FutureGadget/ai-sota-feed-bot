# Decision Log

## 2026-06-14 (story permalinks render briefs, not flattened RSS bodies)
- **Decision:** Story permalink bodies prefer the ranked `summary_1line` and cap a raw `summary` fallback at 320 characters. The brief and thumbnail render as a structured lead card; mechanical `Matches feed focus: ...` ranking text is omitted from the editorial "Why it matters" slot and remains represented by topic chips.
- **Context / Problem:** `/story/c9ab8f8aa14fe295` displayed roughly 1,500 characters of Simon Willison's full RSS article as one paragraph, with a 96px image floated into it. RSS paragraph markup had already been flattened by the durable store, so the result was an unreadable wall of text ending mid-word. This was not produced by a storyline skill: `render_static_pages.py` selected `summary` before the existing 220-character `summary_1line`. The same risk was broad: 430 of 1,054 stored stories had raw summaries over 350 characters and 211 reached the 1,500-character store cap.
- **Rationale:** A story permalink on LLM Digest is a concise memory/share landing page, not a republished article. The deterministic ranking pipeline already creates the appropriate brief; the full text belongs at the original source. Separating image and copy into a responsive card restores scanability, and hiding ranking diagnostics avoids presenting keyword matches as editorial judgment.
- **Impact:** Long RSS, arXiv, release, and community summaries no longer spill onto story pages. SEO/share descriptions use the same concise brief before any substantive why-text. Release highlights and real editorial why-text keep their existing presentation. The underlying durable records and storyline routines are unchanged.
- **Rollback / Alternative:** Revert the renderer change; generated story pages return on the next render. Preserving and rendering sanitized RSS HTML was rejected because it would turn permalinks into partial article mirrors and create a much larger sanitization/layout contract.

## 2026-06-14 (hydrate sitemap stories from page metadata)
- **Decision:** When a sitemap source already fetches an article page for its publication date, collect its real title and description from page metadata in the same request and cache all three fields. Existing publication-only cache rows are refreshed once.
- **Context / Problem:** The empty `/story/<sid>` records were created before the storyline routines ran. `collect_from_sitemap()` synthesized a title from the URL slug and always emitted an empty summary; deterministic ranking then used the title as `summary_1line`, so the durable story store recorded duplicate title/summary content. The storyline scout/editor skills only grouped and narrated those records and could not recover discarded source metadata.
- **Rationale:** Sitemap documents normally expose only URL and modification time, but these sources already opt into a page fetch via `extract_published_from_page`. Parsing Open Graph, Twitter, standard description, title, and publication metadata during that request fixes ingestion without adding network calls or an LLM dependency. The standard-library HTML parser is used so metadata attribute order, entities, and quoted descriptions are handled correctly.
- **Impact:** New items from `anthropic_newsroom`, `anthropic_engineering`, `anthropic_research`, `claude_blog`, and `langchain_blog` carry source-authored titles and summaries into ranking, the story store, story permalinks, and storyline inputs. Existing durable records improve only after the source URL is collected and republished through the normal pipeline; the renderer's thin-page fallback remains necessary for historical records and pages whose source exposes no useful metadata.
- **Rollback / Alternative:** Revert the collector change; cached metadata is additive and older code ignores the extra keys. A separate bulk historical backfill was deferred because it would rewrite runtime data and should be handled as an explicit data migration if needed.

## 2026-06-14 (story/storyline permalinks "earn the click" — kill the empty-page UX)
- **Decision:** Rework `pipeline/render_static_pages.py` story-page rendering so no `/story/<sid>` page renders as a title-only shell or a navigational dead end. Six coordinated changes: (1) drop a body `summary` that case-insensitively equals the `title` (it rendered the title twice — H2 then lead paragraph); (2) thread storyline membership into story pages via a new `storyline_membership()` map `sid -> (slug, label)` and render a prominent "Part of a storyline" up-link box, plus weight co-thread items highest in `related_stories()`; (3) a deterministic framing line ("A brief from <publisher>, published <date>. Open the original below…") for stories with no body content and no storyline box; (4) meta/OG/JSON-LD `description` skips any title-echo candidate and falls back to a synthesized "<source> · <kind> · <date> — tracked on LLM Digest" line; (5) add `📈 Storylines` to the nav on story/daily/weekly pages and a member-aware breadcrumb (Home › Storylines › <thread> › <title>, vs. the old malformed Home › Stories where both pointed to `/`); (6) style the storyline Follow `<button>` as a primary pill with a 44px tap target (it was bare UA chrome), add `clear:both` so the floated thumbnail can't collide, and a `≤480px` image guard. The SEO index gate now also `noindex,follow`s genuinely thin non-member pages (was: off-topic only).
- **Context / Problem:** A UI/UX pass on the live storyline feature found shared/landing `/story/<sid>` pages that look broken: the reported example `https://www.llm-digest.com/story/001317287cdd9d97` ("Fable Mythos Access") showed the title, then the *same string again* as a subtitle, no "why it matters", no body, no tags — just two buttons. Quantified against the local store (1054 stories): **99 (9%) are "thin"** (no `why_it_matters`, no `release_highlights`, and `summary` empty or == title) and **103 have `summary` exactly == `title`**, concentrated in high-signal sources whose links get shared (huggingface_blog 34, anthropic_newsroom 31, claude_blog 14, anthropic_research 12). The emptiest pages were simultaneously rendered as duplicate shells, advertised to Google (sitemap + index), and cut off from the rich storyline timeline they belong to one hop away (the membership data was loaded in `main()` as a bare sid-set and the slug was discarded).
- **Rationale:** Storylines + story permalinks are the product's stated memory / shareable-growth layer (`AGENTS.md` positioning), so they must look credible when shared into HN/Slack/Reddit — "every page earns the click." All fixes are deterministic (LLM is disabled): dedupe is a casefold compare; the up-link reuses already-loaded storyline detail; the framing line uses a small `SOURCE_LABELS` map with a `source_domain()` fallback. Members stay indexable because the up-link + co-thread related make them substantive; only truly contentless non-members are withheld from crawlers, which protects topical authority without breaking shared-link resolution (every story still gets a written page).
- **Impact:** `pipeline/render_static_pages.py` only (no data/config/API change): new `SOURCE_LABELS`/`source_label()`, `storyline_membership()` replaces `storyline_member_sids()`, signatures of `related_stories`/`render_story_body`/`render_story_pages` take `storyline_of`, CSS for `.story-actions button`, and `/storylines` nav on three page types. Verified by re-rendering all 1054 story pages and eyeballing in-browser: the reported empty page now shows a "Part of a storyline → Fable Mythos" box with no duplicate title and an "Anthropic · news · …" OG description; a thin non-member shows the framing line and is `noindex,follow` + out of sitemap; a title==summary page no longer prints the title twice; the Follow button renders as a styled pill. Generated `web/` outputs are intentionally **not** committed here (the hourly `feed-full-publish` pipeline regenerates and commits them — code/runtime-data separation per `docs/status/git-hygiene.md`).
- **Rollback / Alternative:** Revert the `render_static_pages.py` change; the next pipeline run regenerates the prior HTML. Alternatives considered and rejected: (a) hand-edit the generated `web/story/*.html` — they are build outputs, never hand-edited; (b) stop generating pages for thin stories entirely — breaks shared `/s` → `/story/<sid>` redirects; (c) backfill real excerpts via LLM — LLM is disabled by policy. A multi-lens UX audit (5 parallel reviewer agents + synthesis) produced the ranked fix list; lower-priority items deferred: promoting the real title to the page `h1` (currently `📰 Story` is the `h1`), and unifying the storyline TL;DR/What's-new/Why-it-matters typography with the story page's labeled blocks.

## 2026-06-13 (topic-targeted arXiv source `arxiv_llm_reliability`)
- **Decision:** Add a `search_query` mode to the `arxiv_api` collector and a new source `arxiv_llm_reliability` that pulls reliability/hallucination/eval papers across `cs.CL`/`cs.AI`/`cs.LG` via `(cat:cs.CL OR cat:cs.AI OR cat:cs.LG) AND (abs:hallucination OR abs:factuality OR abs:trustworthy OR abs:"LLM evaluation")`. Mapped into the existing `research_watch` slot with `source_bias: -0.25`.
- **Context / Problem:** A reader asked how to surface papers like `arxiv.org/abs/2605.01428` ("Hallucinations Undermine Trust; Metacognition is a Way Forward", `cs.CL`). The category is already ingested via `arxiv_cs_cl`, but each `arxiv_api` source is a per-category latest-N dump sorted by `submittedDate` — a rolling window that misses on-topic papers older than the freshest N, and papers of the same theme living in `cs.AI`/`cs.LG`. The collector only supported a `cat:` query, so a cross-category topic lens required a code change.
- **Rationale:** The reliability/hallucination/eval cluster is squarely the platform-engineer lens (people running LLMs in production care about factuality and evaluation), so a topic-targeted recall source is defensible without breadth drift. The `search_query` field is generic — future topics are config-only. Overlap with the category sources is a non-issue: `dedupe()` (`pipeline/build_tier1.py:85`, `pipeline/build_digest.py:252`) collapses by canonical arXiv URL (plus a 0.85 title-Jaccard backstop) **before** ranking, and the arXiv API returns the same `abs/<id>` for a paper regardless of query, so a duplicate paper from two sources becomes one feed item.
- **Impact:** `collectors/collect.py` (`collect_from_arxiv_api` accepts `search_query` or `category`), `config/sources.yaml` (+1 source), `config/ranking.yaml` + `config/presets/balanced.yaml` (research_watch slot list + `source_bias`). No new slot, no scoring-formula change. Validated end-to-end: `validate_source.py --source arxiv_llm_reliability` collects 30, passes 10 through prefilter, and lands a hallucination-detection paper in the final feed → `✅ EXPOSED`.
- **Rollback / Alternative:** Remove the source from `sources.yaml` + the two ranking files; the collector's `search_query` branch is backward-compatible and can stay. Alternatives considered: (a) just raise `arxiv_cs_cl` `max_results` — only widens within one category, not the theme; (b) loosen the research_watch slot caps — over-exposes all research, not the targeted topic.

- **Rollback / Alternative:** Revert `itemArrivalMs` to `first_seen || published`. Alternative considered: gate catch-up on *both* first_seen and published recency — rejected as more complex than publish-keying, which already matches the user-visible notion of "new".

## 2026-06-13
- **Decision:** Fix "Catch me up" / "new since last visit" showing outdated articles by dropping `collected_at` from the item-recency fallback in `web/index.html`. Recency now resolves to `first_seen || published` (never `collected_at`), via a shared `itemArrivalMs(it)` helper used by both `isNewSinceLastVisit()` and the catch-up `fresh` filter.
- **Context / Problem:** A reader on the live site saw the "⚡ Catch me up" panel ("Since your last visit (Sat, Jun 13): 12 new stories") list articles published days earlier — e.g. "Access OpenAI models … Oracle" (published Jun 10) and "OpenAI to acquire Ona" (Jun 11). The newness test was `Date.parse(it.first_seen || it.collected_at || it.published)`. `collected_at` is the **pipeline build timestamp** — verified identical (`2026-06-13T22:01:07`) for *every* item in `data/processed/latest.json` and always ≈ now — so it is meaningless as a per-item recency signal. Whenever `first_seen` is absent the chain fell through to `collected_at` and flagged **every** item (any age) as new. `first_seen` is absent exactly on the feed API's no-history `mode: latest` path (`api/feed.js` maps base items with `first_seen: null`). The durable run-history path (`accumulateItems`) does populate `first_seen` (earliest run the item appeared in), which is why the live API currently returns correct Jun-11 values — but the `latest` fallback drops it, and that fallback was what the reader hit.
- **Rationale:** `published` is the article's real timestamp and is reliably present on every item (collector output, tier1, processed all carry it); it is already trusted elsewhere (freshness scoring, the tier1 24h fresh-blend gate). Falling back to `published` instead of `collected_at` makes the feature degrade gracefully in `mode: latest`: an article published before the last visit is no longer mislabeled "new." Empirically, replaying the live `/api/feed` payload with `first_seen` nulled (the bug case) and a Sat-Jun-13 last visit: the old chain flagged **37** "new" (including the Jun 10–11 items); the fixed chain flags **8** and excludes every outdated article. The history path (first_seen present) is unchanged (9 → 9).
- **Impact:** `web/index.html` only — a new `itemArrivalMs()` helper plus the two call sites (`isNewSinceLastVisit`, catch-up `fresh` filter). No API, pipeline, data, or config change. Effect: catch-up and the "N new since your last visit" count stop surfacing stale articles when the feed serves its latest-mode payload.
- **Rollback / Alternative:** Revert the `web/index.html` edit to restore the `|| it.collected_at ||` fallback. Considered-but-deferred alternative: backfill real `first_seen` into the API's `mode: latest` path from the durable story store (`data/stories/`, which keeps the true earliest first_seen per `sid`) so latest-mode has exact arrival times rather than the `published` proxy — a larger change (bundle the story shards into `feed.js`) not needed to resolve the reported symptom.

## 2026-06-14
- **Decision:** Revert the `disable_compression: true` PostHog config added earlier today (PR #106 / commit `46a3cd17`). Restore posthog-js default gzip behavior in `web/index.html`.
- **Context / Problem:** The earlier entry (below) attributed the `/e/` ingestion 503s to PostHog rejecting gzip-compressed bodies. A follow-up investigation showed that root cause was **wrong**. Re-debugging the live site with the `disable_compression` fix already deployed: capture POSTs to `/e/` had no `compression=gzip-js` param (so they were already uncompressed) yet **still returned 503 in the browser** — and the 503s vanished the instant uBlock Origin was disabled. Server-side `curl` probes (no browser, no extension) returned `200 {"status":"Ok"}` for **both** an uncompressed POST **and** a genuine `compression=gzip-js` gzip body, with a valid OPTIONS preflight (200, correct CORS for `www.llm-digest.com`). The probe event landed in the PostHog Activity feed. So PostHog never 503'd on gzip; the 503 is a **synthetic response injected by a content/tracking blocker** (uBlock Origin / EasyPrivacy filters block PostHog's `/e/`, `/i/v0/e/`, and `dead-clicks-autocapture.js` paths; the generically-named `array.js`/`config.js`/`surveys.js` loaders pass, which is what made the loss look partial).
- **Why the earlier diagnosis was wrong:** uBlock was active throughout the earlier session. The "uncompressed POST returns 200 / gzip POST 503s" comparison was a false signal — the manual uncompressed test request didn't match the blocklist the way posthog-js's request did, creating a spurious correlation with compression. The events that "started landing" after the flag were server-side test events, not recovered browser traffic.
- **Rationale:** `disable_compression: true` addressed a non-problem; gzip ingestion works fine. Reverting removes a config line added on a false premise and keeps the decision log accurate so a future PostHog-503 investigation isn't misdirected toward compression. The real lesson: **a tracking 503 that only reproduces in-browser and not via `curl` is almost always a client-side ad/tracking blocker, not a server/encoding bug.**
- **Impact:** `web/index.html` posthog init only (one config line + comment removed). No behavior change for real users — gzip ingestion already returned 200. No pipeline, data, or API change.
- **Follow-up (optional, not done):** If recovering blocker-using visitors matters, the proper fix is a PostHog **reverse proxy** — route events through a first-party path (e.g. `https://www.llm-digest.com/ingest/*` via a `vercel.json` rewrite) so requests aren't matched by tracker blocklists. Tracked as a possible future enhancement, not implemented here.

## 2026-06-14
- ⚠️ **Superseded by the entry above (root cause was wrong).** The 503s were caused by a client-side ad/tracking blocker, not gzip compression. Kept for historical record.
- **Decision:** Disable PostHog client-side request compression by adding `disable_compression: true` to the `posthog.init(...)` config in `web/index.html`.
- **Context / Problem:** Reader analytics stopped landing. Debugging the live site in Chrome showed every event-capture POST to `https://us.i.posthog.com/e/?...&compression=gzip-js` returning **HTTP 503**, with posthog-js retrying (retry_count=1..4) and all retries also 503. Billing was not the cause — Free plan, only ~1.5K/1M events used this cycle. Isolation tests pinned it to the request body encoding: a **plain (uncompressed) POST** to `/e/` returned `200 {"status":"Ok"}` and a **GET beacon** returned 200, while only the **gzip-js-compressed POST** 503'd. posthog-js v1.386.6 gzips capture bodies by default.
- **Rationale:** PostHog's ingestion endpoint for this project rejects gzip-compressed bodies with 503 but accepts uncompressed ones. Setting `disable_compression: true` makes posthog-js send uncompressed payloads. Validated live in-browser: setting the flag on the running instance made the capture POST return 200 immediately. Our event payloads are tiny, so the bandwidth cost of skipping gzip is negligible. This is the minimal, lowest-risk fix and keeps the analytics loop working regardless of whether the PostHog-side gzip issue is later resolved.
- **Impact:** `web/index.html` posthog init only (one config line + comment). No pipeline, data, or API change. Effect: reader analytics events (`page_view`, `click`, `item_save`, etc.) ingest successfully again.
- **Rollback / Alternative:** Remove the `disable_compression: true` line to restore default gzip behavior (only safe once PostHog stops 503ing compressed bodies). Alternative considered: opening a PostHog support ticket for the gzip 503 — worth doing in parallel, but the client-side flag is the immediate unblock.

## 2026-06-14
- **Decision:** Move the `feed-full-publish.yml` schedule off the top of the hour, from `cron: "0 * * * *"` to `cron: "37 * * * *"`.
- **Context / Problem:** The hourly feed pipeline was firing only ~6×/day instead of 24×. The scout proposes thread links the anchor-pair rule structurally misses (same story under different vocabulary; emerging near-miss threads); confirmed links are written to a durable sidecar (`data/storylines/scout/links.json`) that `build_storylines.py` applies as synthetic candidates **through the same MIN_ITEMS/MIN_DAYS/MIN_SOURCES floor** — the deterministic gate. Selection that reaches readers always passes that floor, never raw LLM output.
- **Context / Problem:** `build_storylines.py` clusters on shared *rare anchor tokens*, which is deliberately precision-first and therefore misses real threads: a launch covered as "OpenAI's new flagship" and "GPT-5 is here" shares no rare anchor, so the two never join; and a genuinely developing story sitting one item/day/source under the floor never surfaces. We wanted agents to do more of the intelligent work, but replacing the clustering with LLM judgment would break three things: stable membership (slugs carry over by member overlap so follows survive recluster jitter — LLM re-clustering thrashes membership and silently breaks follows), the "one shared deterministic ranking for everyone, not a filter bubble" product belief (a storyline is a trust surface), and the cheap must-stay-green hourly heartbeat (an LLM pass over a 21-day window every hour is real tokens + a new failure mode).
- **Rationale:** Keep deterministic clustering as the spine; add the agent only where LLM judgment beats token-matching (semantic links across vocabulary, near-miss promotion, labeling). The integration mirrors the `storyline-editor` narrative sidecar: a script does the cheap, exact, reproducible prep (`pipeline/scout_candidates.py` enumerates near-miss anchors and broad-token co-mention buckets into a tight bundle — the token-efficiency lever), Haiku subagents do only the judgment on that pre-filtered set ("are these the same story/thread?", high-precision, default-to-no), and the deterministic builder applies confirmed links through the existing floor. A scout link is inert unless its nodes clear the floor, and it joins any candidate it shares a node with (extends an existing thread rather than spawning a duplicate). Threads that used a scout link carry a `via_scout` flag for transparency (anti-hype: show how it was found). Pure-Haiku-without-script was rejected — it pays tokens to read the whole store and badly re-derive cheap deterministic facts (dates/sources/dedup).
- **Impact:** New `pipeline/scout_candidates.py` (deterministic candidate generator → `data/storylines/scout/candidates.json`). `pipeline/build_storylines.py` `cluster()` injects scout links from `scout/links.json` as floor-gated synthetic candidates and sets `via_scout`. New `.agents/skills/storyline-scout/` (SKILL.md + `scout_common.py`, `validate_links.py`, `seed_scout_sample.py`, `run_scout.sh`; documents a Haiku `ultracode` Workflow fan-out with adversarial verification). `web/storyline.html` renders a "🔍 surfaced by scout" badge. `vercel.json` excludes `data/storylines/scout/**`. Docs: `AGENTS.md`, `db-schema.md`. Behavior is unchanged when no links file exists (regression-safe).
- **Rollback / Alternative:** Delete `data/storylines/scout/links.json` (or revert the `cluster()` injection) — the next run regenerates clean threads with zero scout influence. Alternatives considered: let the agent emit storylines directly (rejected — bypasses the floor, destabilizes slugs/follows); apply links at the dedup/node level (rejected for v1 — collapses multi-day arcs into one node; thread-level links keep the timeline intact); fuzzy/embedding similarity in the deterministic layer (rejected — non-explainable on a trust surface; the agent is the judgment layer, gated by the floor).

## 2026-06-13
- **Decision:** Cap `data/tier1/runs/` retention at a **3-day hard delete** (no daily/weekly archive tail), down from "14d high-res + 1/day for a year". Added an optional `max_age_days` hard cutoff to `pipeline/prune_runtime_data.py` and wired `--tier1-max-age-days` (default 3) in `run_full.sh`. Processed snapshots keep their 45d + archive tail unchanged.
- **Context / Problem:** `api/feed.js` and `api/rss.js` bundle `tier1/runs/**` into their Vercel serverless functions (`vercel.json` `includeFiles`). tier1 snapshots are heavy (~1.3–1.7 MB each, ~8/day) and the old retention kept ~14 days high-res then 1/day for a full year — so the dir had grown to ~122 MB and was on track to rebuild the 250 MB function-size failure already fixed once in commit `1fe029de`. A live deploy failure would freeze the site, because each hourly data commit *is* the deploy that ships fresh feed data (no DB).
- **Rationale:** Verified against the consuming code that nothing reads tier1 snapshots older than ~24h: `feed.js readTier1Recent` and `rss.js loadTier1Recent` both use a 24h lookback for the "fresh-blend" overlay, and `mergeTier1Fresh` hard-rejects items older than 24h by publish date (`maxFreshAgeMs`), so even the tunable `tier1_lookback_hours` ceiling (168h) cannot surface older items. RSS's 7-day window is built from `processed/runs` (small files), not tier1. `share.js` resolves share URLs via the durable `stories/index.json` first and only scans the *newest* runs as a fallback, so trimming old tier1 runs is invisible to it. 3 days = the 24h read window plus a generous buffer. The durable memory layer (`stories/`, `storylines/`, `daily/`, `weekly/`) reads none of tier1/runs, so storyline/permalink/recap durability is unaffected. Corrects an earlier mistaken assumption that tier1 needed ≥7 days for RSS.
- **Impact:** Dry run on the current store: tier1 runs 96 → 21 files (75 deleted, ~97 MB freed); bundled tier1 drops ~122 MB → ~31 MB, taking the `feed.js` data bundle from ~158 MB → ~67 MB and restoring comfortable headroom under the 250 MB limit. Zero customer-facing behavior change (feed, fresh-blend, RSS 7-day window, date-range browsing, storylines, permalinks, recaps all identical). Only loss: high-resolution tier1 audit/replay beyond 3 days — an ops artifact no surface reads. Docs: `AGENTS.md`, `docs/generated/db-schema.md`.
- **Known residual:** `feed.js` still clamps `tier1_lookback_hours` to 168h / `tier1_max_runs` to 48 — vestigial ceilings retention can no longer honor, but harmless because `mergeTier1Fresh` filters to 24h publish age. Left as-is to keep the change minimal; could be lowered to ~72h/24 for contract honesty in a separate cleanup.
- **Rollback / Alternative:** Set `TIER1_RUN_MAX_AGE_DAYS=0` (disables the cap) and `TIER1_RUN_RETENTION_DAYS` back to 14 in `run_full.sh`; next run restores the prior retention shape. Deleted snapshots are not recoverable, but nothing reads them. Alternatives considered: drop `tier1/runs/**` from `vercel.json` `includeFiles` entirely and serve only `tier1/latest.json` (rejected — fresh-blend dedupes across the last few runs, so it needs recent run history, just not 100+ MB of it); move served blobs to object storage (rejected as over-engineering for the current size — retention cap is sufficient).

## 2026-06-14
- **Decision:** A batch of SEO/discoverability changes, all in the static-render layer and hand-edited shells (no pipeline/ranking change): (1) unify the canonical domain (`llms.txt`/`llm-guide.txt` pointed at `ai-sota-feed-bot.vercel.app` while everything else used `www.llm-digest.com`); (2) render a static `web/storyline/<slug>.html` per storyline timeline file and route `/storyline/<slug>` to it (was a JS shell, invisible to crawlers and absent from the sitemap); (3) `robots=noindex,follow` + sitemap exclusion for off-topic story permalinks (`is_on_topic` gate); (4) upgrade structured data to `NewsArticle` + `BreadcrumbList` with a publisher `logo` and `isBasedOn`, plus `WebSite`+`Organization` on the homepage; (5) a branded default OG card (`og-default.png`) + `logo.png` + `favicon.svg`, with `summary_large_image` Twitter cards; (6) a keyword-aligned homepage `<h1>` + a `<noscript>` crawlable fallback; (7) `lastmod` for the `/voices` and weekly sitemap rows.
- **Context / Problem:** Story permalinks already had solid per-page SEO, but the highest-value growth surface — storylines ("what happened next with X"), the stated structural moat and the thing shared into HN/Slack — had **zero** SEO presence: `/storyline/<slug>` was client-rendered (`web/storyline.html` `innerHTML` after `fetch`) and the sitemap carried 0 storyline URLs vs 1040 `/story/`. The split canonical domain diluted ranking signal. Off-topic permalinks (e.g. a frontier lab's "community investments in Missouri", "gardening tips") that slip through the feed were getting thin indexable pages, diluting the "AI platform engineer" topical authority. The homepage `<h1>` was a generic `📰 AI Feed`, the feed was JS-only (no crawlable content), there were no social cards, and no favicon at all.
- **Rationale:** Keep the work in the deterministic static-render layer (`pipeline/render_static_pages.py`) where it composes with the existing daily/weekly/story rendering and stays LLM-free. Storyline timeline files are **never pruned** (shared-link durability), so a static page is rendered for *every* detail file — guaranteeing `/storyline/<slug>` always resolves — while only **active** (in-index) threads enter the sitemap to keep it focused. Off-topic pages stay *rendered* (shared links must resolve) but `noindex,follow` so link equity still flows to related stories; the gate is conservative (index unless there's no AI/platform signal at all, and never noindex a release/paper/research item or a storyline member) to avoid suppressing real content. The static storyline page keeps a minimal Follow button that mirrors `web/storyline.html`'s `localStorage` key (`ai_feed_storyline_follows_v1`) so follows stay consistent across the static page and the dynamic index. The default OG card is derived from the canonical origin so a custom `--base-url` stays correct. Homepage gets `WebSite`+`Organization` but intentionally **no** `SearchAction` (the feed search is client-side with no indexable results URL, so a sitelinks-searchbox target would be a broken claim).

New `scripts/make_og_assets.py` + `web/{og-default.png,logo.png,favicon.svg}`. Hand-edited shells (`index.html`, `daily/weekly/voices/storyline.html`) gain favicon + default OG card + `summary_large_image`; `index.html` gains the new `<h1>`/`.h1-sub`, the `<noscript>` block, and `WebSite`/`Organization` JSON-LD. Docs: this ADR, `AGENTS.md`, `web/llms.txt`, the `render_static_pages.py` docstring.

Per-item rollback is independent (e.g. drop only the `noindex` gate by making `is_on_topic` return `True`). Alternatives considered: keep `/storyline/<slug>` on the JS shell and rely on Google's JS rendering (rejected — unreliable and still absent from the sitemap); fix off-topic pages upstream in `config/profile.yaml`/ranking (rejected for this change — riskier, changes what the feed shows; the render-layer gate is self-contained and reversible); add `SearchAction` (rejected — no real search-results URL to point at).

## 2026-06-14 (Bubble Buddy — 3D site mascot)
- **Decision:** Add a procedurally-generated **WebGL/Three.js mascot** ("Bubble Buddy") that floats into the bottom-right corner of the site at random intervals, idles for a few seconds, and tucks away again. The character is a translucent blue **bubble** — a deliberate tie to the site's 🫧 hype-flag motif and the "digest" theme — designed against the cuteness brief (Kindchenschema + chibi proportions + circle-only shape language) **and** an explicit "cute *and* intelligent" goal (it's an AI *intelligence* bot): one oversized squishy head-body with an inner glow, big wide-set sparkly eyes set *low* on the face (large forehead) whose pupils drift/"look around", expressive eyebrows, **round glasses** + a glowing **gold idea-antenna** as the smart cues, a tiny smile, blush, stubby pigeon-toed feet and nub arms, plus a few gold "thinking" sparkles orbiting it. On poke it raises its brows, grins, waves, and bursts sparkles. (v1 was a plain featureless bubble — the owner felt it read cute-but-not-smart, so the glasses/antenna/expression pass was added.) New module `web/mascot/mascot.js`; lazy-loader snippet added to the five hand-edited shells and to the static-render template (`pipeline/render_static_pages.py`) so every generated page (`/story`, `/daily`, `/weekly`, `/storyline`) gets it too.
- **Context / Problem:** Owner wants a recognizable, on-brand mascot that "resides in the website and randomly appears" — a low-cost personality/retention touch — without compromising the site's core value of being a fast, finishable, anti-hype feed (Speed Insights + CLS work shipped the same week). A naïve always-on 3D widget would fight exactly that.
- **Rationale:** Genuine 3D (chosen by the owner over a CSS/SVG fake) is delivered with a hard **performance contract** so it never touches the critical path: (1) Three.js (~150 KB) is `import()`-ed only on the *first* scheduled appearance (7–14 s after idle), so initial load pays nothing; (2) the render loop runs **only** while the buddy is on screen and is fully parked (no rAF, no GPU) between appearances and whenever the tab is hidden; (3) `position:fixed` overlay added post-load → **zero CLS**; pixel-ratio capped at 2, tiny 150×185 canvas, geometry built in-code (no binary model asset to host/commit). The character is **theme-aware** (re-tints live on `data-theme` change via a `MutationObserver`) and **motion-respecting** (`prefers-reduced-motion` → it never loads). It is decorative and fully defensive: no WebGL, a blocked CDN, or any error silently no-ops. A session-scoped dismiss "×" and `sessionStorage` opt-out keep it polite; `window.__bubbleBuddy.appearNow()/hide()` are exposed for QA and for a future "you're all caught up" summon. Three.js is loaded from a pinned unpkg URL (consistent with the existing oat.ink CDN usage) — acceptable because the mascot is non-essential and failure is invisible.
- **Impact:** New `web/mascot/mascot.js` (~570 lines, self-contained, self-initializing on import). Identical lazy-loader `<script type="module">` before `</body>` in `web/{index,daily,weekly,storyline,voices}.html` and in the shared `render_static_pages.py` HTML template (so generated pages carry it; regenerated on the next hourly run — not committed in this change to keep code separate from runtime artifacts). No pipeline/ranking/data/config change; no new dependency in `requirements.txt`/`package.json` (Three.js is a runtime CDN import, not a build dep). Verified in a real browser (Playwright + WebGL): renders correctly in light and dark themes, the poke reaction (on-brand speech bubble + bubble-burst) fires, and the renderer parks between appearances.
- **Rollback / Alternative:** Delete `web/mascot/` and remove the loader snippet from the five shells + the `render_static_pages.py` template (next render drops it from generated pages). Alternatives considered: CSS/SVG pseudo-3D (lighter, but owner explicitly wanted true 3D); a pre-baked GLB model file (rejected — committing a binary asset and hosting it is heavier than building the simple geometry in-code); always-visible mascot (rejected — fights the finishable/low-distraction positioning; the random brief appearance is the point).
- **Follow-up (portable/modular refactor):** Owner wanted to place the mascot anywhere on the site, not just the hardcoded bottom-right corner. Refactored the self-running IIFE singleton into a **`createBubbleBuddy(options)` factory** (ESM `export` + `default`): all render state moved from module scope into per-instance closures, so **multiple independent instances** can coexist; the Three.js import is shared across them (cached promise, imported once). Three usage modes, all backward-compatible: (1) **drop-in** — importing the module still auto-creates one floating mascot, now tunable via `window.BubbleBuddyConfig` or opt-out with `= false`; (2) **declarative** — every `[data-bubble-buddy]` anchor on the page gets its own mascot filling that box, configured via `data-*` attrs (if any anchor exists, the default floating one is suppressed so the page owns placement); (3) **programmatic** — `createBubbleBuddy({ mount, position, tips, colors, autostart, … })` returning an instance API (`appearNow/start/stop/hide/destroy/getState/el`). Added `mount` (Element|selector), `position` (four corners or `'fill'`), size/offset/timing/`tips`/`colors`/`dismissible`/`storageKey`/`ariaLabel` options; `applyPalette` switched from `setHex` to `Color.set` so `colors` accepts hex numbers or CSS strings; `destroy()` disposes geometries/materials, the renderer (with `forceContextLoss`), observers, and listeners. The existing five-shell + `render_static_pages.py` loader snippets are unchanged and still yield the single floating mascot. New `web/mascot/README.md` documents all three modes + the options table. Verified in-browser (Playwright + WebGL): factory/default/global exports present, default auto-mount + a programmatic instance render as two **distinct** WebGL contexts, a `[data-bubble-buddy]` anchor mounts in place, and `hide()`/`destroy()` clean up without leaks. `web/mascot/mascot.js` is now ~745 lines.

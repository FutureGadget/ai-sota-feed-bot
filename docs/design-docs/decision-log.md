# Decision Log

## 2026-07-04 (Add CORS handling to the PostHog proxy Worker)
- **Decision:** Make `infra/llm-digest-proxy-worker` terminate CORS for the first-party PostHog proxy: respond to `OPTIONS` preflights, allow `https://www.llm-digest.com` / `https://llm-digest.com` plus localhost development origins, echo requested headers, and wrap both cached asset responses and ingest API responses with `Access-Control-Allow-Origin` and `Access-Control-Allow-Credentials`. Mark the Worker package as ESM and add a Node smoke test for preflight, cached `/array/*` assets, and forwarded ingest requests.
- **Context / Problem:** Production loaded `posthog-client.js` from `www.llm-digest.com`, but the PostHog snippet then fetched `https://assets.llm-digest.com/array/<project>/config.js` with `crossOrigin="anonymous"`. The proxy returned `200 OK` from PostHog's asset host, but without `Access-Control-Allow-Origin`, so the browser rejected the response and the SDK bootstrap failed before pageview/analytics events could flow.
- **Rationale:** The proxy owns the browser-facing origin, so it must not depend on upstream PostHog asset/API responses carrying CORS headers for `llm-digest.com`. Wrapping cached responses is required because the Worker stores upstream asset responses in `caches.default`; adding headers only on cache miss would keep the failure for hot assets.
- **Impact:** `infra/llm-digest-proxy-worker/src/index.js`, `infra/llm-digest-proxy-worker/package.json`, `tests/test_posthog_proxy_worker.mjs`, and the PostHog runbook changed. No site UI, ranking, data artifact, or analytics event schema change.
- **Rollback:** Revert the Worker and test changes, or set `POSTHOG_HOST=https://us.i.posthog.com` in Vercel to bypass the proxy while the Worker is fixed.

## 2026-07-03 (Emit the standard `$pageview` so PostHog Web Analytics activates)
- **Decision:** In `web/posthog-client.js`, let posthog-js capture the standard pageview — `capture_pageview: 'history_change'` (SPA-aware) — and delete the hand-rolled `sdk.capture('page_view', …)`. Bump the wrapper asset version so cached copies of the old pageview-only client are busted. Update `pipeline/north_star_metric.py` to count `event IN ('$pageview', 'page_view')` so the returning-reader rollup bridges the rename with no gap.
- **Context / Problem:** PostHog Web Analytics reported 0 visitors / 0 views / 0 sessions over a full month of real traffic (~27 users) even though the site had captured ~1,300 pageview-shaped events. The cause: the client emitted a **custom** `page_view` event (with `capture_pageview: false`), and Web Analytics only counts the standard `$pageview`. `$pageview` did not exist in the project taxonomy at all, so every Web Analytics KPI (visitors, sessions, bounce rate, top pages, channels) was dark despite declared intent to use the product. The SDK was otherwise loaded and autocapturing (`$pageleave`, `$web_vitals` were firing).
- **Rationale:** The custom `page_view` already carried every property Web Analytics needs (`$current_url`, `$pathname`, `$referrer`, `$geoip_*`, device/browser/os), so switching to the standard event is a drop-in with no data loss — it just uses the name the product recognizes. `'history_change'` (the modern default) covers both full page loads on the static pages and any client-side URL changes on the feed shell. The north-star query is widened to both names rather than swapped, so historical `page_view` weeks and future `$pageview` weeks both count and the metric never goes dark across the transition.
- **Impact:** `web/posthog-client.js`, wrapper asset version in `pipeline/render_static_pages.py` + hand-authored shells + the two committed generated shells (`web/map.html`, `web/foundations.html`), `pipeline/north_star_metric.py` (query + docstring), and the `tests/test_site_chrome.py` contract assertions changed. Generated detail pages pick up the new wrapper version on the normal static render path (regenerated at deploy by `scripts/vercel_build.py`). No ranking, feed data, or API schema change.
- **Rollback:** Restore `capture_pageview: false` and the manual `sdk.capture('page_view', …)` in the wrapper, revert the wrapper version, and narrow the north-star query back to `event = 'page_view'`. Web Analytics returns to dark; product analytics is unaffected.

All four feed-pipeline health-scout discriminators — build-skip surge, circuit-breaker cluster, source-failure clustering, and pipeline stall — were unqueryable, so every scout run returned "nothing found," which reads as "healthy" when it actually means "blind."

The capture path is optional and non-fatal: with no project write key (local runs, secret-less CI) every call no-ops cleanly and never raises, matching the repo's "fail gracefully when optional integrations are missing" guardrail. The write key (`phc_…`) is a distinct credential from the `POSTHOG_PERSONAL_API_KEY` the read-side HogQL helpers use.
- **Impact:** New `pipeline/telemetry.py` + `tests/test_telemetry.py`; capture calls added at the completion/skip/failure points of `collectors/collect.py`, `pipeline/build_digest.py`, `pipeline/source_health.py`; `feed-full-publish.yml` gains the two env vars. No schema, API, or web-surface change. **The `POSTHOG_PROJECT_API_KEY` GitHub secret must be added to the repo before the events flow in CI** — until then the calls no-op. Transport + payload shape validated live (HTTP 200) against the project.
- **Rollback:** Remove the env vars from the workflow (events immediately stop; scout returns to blind), or revert the commit to drop the helper and capture calls entirely.

## 2026-07-02 (Stage the email cursor before the "no change" check so its first write commits)
- **Decision:** In `email-digest.yml`'s "Commit send cursor" step, replace the `git diff --quiet -- data/email/state.json` guard with: no-op when the file is absent, otherwise `git add` first and check `git diff --cached --quiet`. No change to `publish/publish_email.py`.
- **Context / Problem:** `data/email/state.json` had never been committed. `publish_email.py` writes the cursor only after a successful send, so in every fresh workflow checkout the file was *untracked* — and `git diff` never reports untracked files, so the guard always printed "no cursor change to commit" and exited before `git add`. Every run therefore started with no cursor: the daily `last_sent_date` guard was ineffective (on 2026-06-30, two dispatches at 23:00 and 23:29 UTC each sent the same daily brief), and `storylines.sent_through`/`seen_sids` never advanced, so "Continuing threads" repeated the same threads day after day (`threads=3` in every recent run).
- **Rationale:** Staging before diffing makes the guard see the untracked first write while keeping the intended no-ops: file absent (secrets-gated no-op run) and file unchanged (guard-skipped run) both exit cleanly. Fixing the workflow rather than the Python keeps `publish_email.py`'s "advance the cursor only after a successful send" contract intact.
- **Impact:** `.github/workflows/email-digest.yml` only. After the first post-merge send commits the cursor, the double-send guard and storyline delta logic work as designed; the repeated-threads symptom self-heals on the next send. Verified all four file states (absent / untracked / tracked-unchanged / tracked-modified) in a scratch repo.
- **Rollback:** Revert the workflow step; behavior returns to send-without-cursor (double-send risk and repeating threads).

- **Context / Problem:** `build_storylines.py` clusters on shared *rare anchor tokens*, which is deliberately precision-first and therefore misses real threads: a launch covered as "OpenAI's new flagship" and "GPT-5 is here" shares no rare anchor, so the two never join; and a genuinely developing story sitting one item/day/source under the floor never surfaces. We wanted agents to do more of the intelligent work, but replacing the clustering with LLM judgment would break three things: stable membership (slugs carry over by member overlap so follows survive recluster jitter — LLM re-clustering thrashes membership and silently breaks follows), the "one shared deterministic ranking for everyone, not a filter bubble" product belief (a storyline is a trust surface), and the cheap must-stay-green hourly heartbeat (an LLM pass over a 21-day window every hour is real tokens + a new failure mode).

Threads that used a scout link carry a `via_scout` flag for transparency (anti-hype: show how it was found). Pure-Haiku-without-script was rejected — it pays tokens to read the whole store and badly re-derive cheap deterministic facts (dates/sources/dedup).

- **Context / Problem:** All Vercel deploys (production + PR previews) began failing with `A Serverless Function has exceeded the unzipped maximum size of 250 MB`, freezing the site (production stuck on ~00:08 data; PR #134 previews red). **Key root cause:** Vercel bundles the *entire uploaded project* into **each** serverless function (minus that function's `excludeFiles`) — this is why `api/client-config.js` already carries `excludeFiles: data/**`. `data/` had grown to **366 MB**, dominated by `data/tier1/runs` (175 MB) and `data/raw` (125 MB). Net product impact: the live feed's "⚡ Fresh" lane is built from the single latest tier1 snapshot instead of a 24 h union across runs (minor); RSS loses a small tier1 fresh-blend bonus; share/permalinks/recaps/storylines/map unaffected. Measured: total uploaded project drops **386 MB → 68 MB**, so every function bundle is comfortably under 250 MB. Chosen over (a) adding broad `excludeFiles` to every function (fragile, repeats per function) and (b) cutting tier1 retention to ~1 day (loses git-side audit history the 2026-06-13 prune ADR deliberately kept; doesn't address the 125 MB `raw/`).
- **Impact:** New root `.vercelignore`. `vercel.json` `feed.js`/`rss.js`/`share.js` `includeFiles` also no longer list `tier1/runs/**` (coherent with it being unignorable now), but that is cosmetic — the `.vercelignore` is what fixes the size. No code, data, or retention change. Docs: `AGENTS.md` Data Artifacts retention note, this ADR. Shipped on the PR #134 branch so its preview can deploy green and to unblock production on merge.
- **Rollback / Alternative:** Delete `.vercelignore` (or remove specific lines) — but only after the corresponding dir is small enough to fit, since the default bundle is everything. When the resulting bundle has zero genuine articles, the script itself advances `state.json`'s cursor past that date (`record_skipped_date`) before returning `"empty": true` — an explicit `--date` call never touches this state. The `daily-recap` prompt was rewritten to branch on the script's `due`/`empty` fields instead of doing its own date arithmetic, and its commit step now distinguishes three outcomes: a published recap, a state-only "skip" commit, or no changes at all.
- **Context / Problem:** The same-day prior fix ("latest published + 1 day", computed in the prompt) closed the failed-run gap but opened a new one: if a target day genuinely had zero articles, step 3 said "stop successfully without publishing" with no durable record of the attempt. Since nothing advanced the cursor, the *next* run would recompute the exact same target date, find the same empty bundle, and stop again — forever. One empty day (source outage, circuit-breaker trip) would have permanently wedged every subsequent daily recap. A related risk was also caught during design: if the empty-day cursor lived only in the prompt's reasoning (not a script-owned, committed file), a cloud routine run starting from a fresh checkout each time would simply lose that state the moment the run ended, silently undoing the fix.
- **Rationale:** Deriving the target date in code (not agent prose) makes the rule testable and removes a class of agent arithmetic mistakes — matches the same philosophy as the prior weekly-recap review. Keeping the "confirmed empty" signal in a durable, git-committed `data/daily/state.json` (rather than only in the prompt's momentary reasoning) is what actually makes the cursor survive across independent routine runs; the prompt's new three-way commit branch (recap / skip-only / no-op) exists specifically so that a state-only cursor advance still gets committed and pushed even when no recap is published. Scoping `record_skipped_date` to automatic mode only (never on an explicit `--date` call) keeps manual backfills/testing from mutating production cursor state.
- **Impact:** `.agents/skills/daily-summary/scripts/daily_common.py` (new `DAILY_STATE_PATH`, `latest_published_date`, `read_state`, `record_skipped_date`, `next_target_date`), `build_daily_input.py` (automatic-mode target resolution, `due`/`empty` result fields), `.agents/routines/daily-recap/prompt.md` (branches on script output; three-way commit step), `.agents/routines/daily-recap/harness.yaml` (comment only), `.agents/skills/daily-summary/SKILL.md` (usage comment). New `data/daily/state.json` artifact (not yet present in the committed tree; created on first automatic run that finds an empty day). New `tests/test_daily_recap_cursor.py` (5 tests, isolated temp-dir fixtures, never touches the real `data/daily/`). Full suite: 117 tests + 34 subtests pass. Verified the CLI end-to-end against a scratch fixture: bootstrap-to-yesterday, empty-day cursor advance + second-run rollover, `due: false` no-op at the current-day boundary, and an explicit `--date` call leaving `state.json` untouched.
- **Rollback:** Revert to the prompt-only "find the latest file, add one day" logic from the prior entry, or further back to "yesterday's UTC calendar date" if the state-based approach proves troublesome. Delete `data/daily/state.json` to reset the cursor to bootstrap (next run falls back to yesterday).

## 2026-07-03 (Fix: "New"/"Catch me up" resurfacing weeks-old stories that drop out and re-enter the ranked window)
- **Decision:** In `api/feed.js`, compute `accumulateItems()` over the FULL unbounded run history read by `readRuns()`, not the caller's `from`/`to`-filtered run subset. The `from`/`to` window continues to gate which *runs* appear in the diagnostic `runs` summary and which *items* are displayed at all (via the existing `filterItemsByPublishWindow`), but no longer gates which runs are scanned to compute `first_seen`/`last_seen`/`seen_count`.
- **Context / Problem:** A reader reported "Claude Fable 5 and Claude Mythos 5" (`anthropic_newsroom`) showing in the "⚡ Catch me up" brief as though it just arrived, despite being weeks old. Tracing the data: the story first reached the ranked window on 2026-06-15, then dropped out of ranking for over two weeks before reappearing in a run on 2026-07-02. The default feed UI request window is only the last 7 days (`presetDaysState = '7'`, `web/index.html`). `readRuns()` already reads every retained run file unconditionally (no I/O is saved by date-bounding), but the handler discarded every run outside the requested window *before* calling `accumulateItems()` — so for any item whose only occurrence inside that 7-day window was its 2026-07-02 re-entry, the computed `first_seen` became 2026-07-02 instead of its true 2026-06-15 arrival. Per `docs/product-specs/live-feed.md`, "New"/"Catch me up" are keyed exclusively off `first_seen` (never falling back to `published` when present), so this made any story that temporarily fell out of the ranked window and later re-ranked look brand new again — the opposite of the intended "resurfaced stories should still count as new only once" behavior, undermining the transparent/anti-hype product pillar.
- **Rationale:** `first_seen` is documented as "the run_at when the item first reached the ranked window" — an absolute, not a window-relative, timestamp. Scanning full history to compute it is free (the files were already being read into memory for every request regardless of window) and item *display* was already correctly gated by `filterItemsByPublishWindow` against `published`/`first_seen`/`last_seen`, so decoupling "which runs establish arrival time" from "which items are shown in this window" is a minimal, targeted fix with no other behavioral change.
- **Impact:** `api/feed.js` (`baseItems = accumulateItems(runs)` instead of `accumulateItems(filteredRuns)`). New `tests/test_feed_first_seen_window.mjs` pins the regression against synthetic fixture runs (confirmed it fails on the pre-fix code with the exact real-world dates). Full JS suite (22 tests) passes. No schema, ranking, or UI change — the frontend "New"/"Catch me up" logic (`web/index.html`) is unchanged and already correct; it was only ever fed a wrong `first_seen` value.
- **Rollback:** Revert to `accumulateItems(filteredRuns)`; delete `tests/test_feed_first_seen_window.mjs`.

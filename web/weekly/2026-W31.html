MCP Goes Stateless: the Protocol and Platform Layer for Agent Builders 8 items

The Model Context Protocol's largest spec revision since launch went stateless this week, and the platforms builders actually deploy on responded in lockstep with governance, cost, and security layers.

MCP is going stateless: What the new spec means for AI agents

hackernews_aiDetails

The new MCP spec drops persistent server state, changing how builders architect agent-to-tool connections.

Playbook takeaway

ProblemMCP's old session-handshake spec pins each session to one server instance, so a load balancer routing a follow-up call to a different pod returns a 404 unless you bolt on sticky sessions or a shared Redis session store.

ApplyAdopt the new MCP spec, which drops the mcp-session-id entirely — each request now carries protocol version, client identity, and capabilities in a _meta object, so any server instance can handle any request. Redeploy MCP servers behind a plain round-robin load balancer or serverless containers instead of maintaining instance affinity or a session store, and benchmark the added per-call payload against your real request volume before rollout.

ExpectedThe spec authors report MCP servers now scale like any other stateless HTTP service — no sticky-session config, no Redis provisioning, no careful deployment drains.

How AgentCore Gateway supports the MCP 2026-07-28 spec

aws_ml_blogDetails

AWS details the MCP 2026-07-28 spec, stateless by default with a governed extensions system and hardened authorization, and how AgentCore Gateway supports it.

Playbook takeaway

ProblemThe MCP 2026-07-28 spec dropped the initialize handshake and Mcp-Session-Id header, and remapped several JSON-RPC error codes to real HTTP status codes.

ApplyStop relying on session state or persistent connections in your MCP client code — pass state through tool parameters instead. Update error handling for the changed codes (unknown method → HTTP 404, resource-not-found moved from -32002 to -32602, unsupported version → HTTP 400/-32022), and send the MCP-Protocol-Version header on every request since omitting it silently falls back to 2025-03-26. On your gateway, run one UpdateGateway call adding 2026-07-28 to supportedVersions alongside your existing versions.

ExpectedServers stop needing sticky sessions and can scale horizontally behind a plain load balancer, while old and new clients keep working through the 12-month deprecation window.

Article: Securing MCP in Production: Defense-in-Depth Beyond the Gateway

infoq_ai_mlDetails

A defense-in-depth architecture for securing MCP in production spans four control layers, from safe execution to outbound traffic.

Playbook takeaway

ProblemMCP tool handlers that build shell commands via string interpolation are exploitable through parameters the model controls, and a perimeter gateway alone doesn't stop it.

ApplyReplace string-interpolated exec()/eval()/subprocess.run(shell=True) calls in tool handlers with array-argument execution (e.g. execFile()), and add a CI gate (Semgrep rules) that blocks those unsafe patterns from merging. Pair it with an egress allow-list via NetworkPolicy so a compromised tool can't reach arbitrary outbound hosts.

ExpectedCloses the two cheapest attack paths — injected shell commands and unrestricted outbound calls — for close to zero runtime cost.

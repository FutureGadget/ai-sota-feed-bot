Proving agent ROI and measuring cost efficiency is hard

🧱 Obstacle·cost·active·9 entries·9 sources·updated 2026-10-06

Calculating the true return on investment (ROI) for agent systems is blocked by the difficulty of measuring time savings, tracking per-task token usage, and accounting for hidden costs like token inflation in quantized models. Platform engineers must move from generic productivity claims to instrumented cost-per-task accounting and evidence-based measurement of outcomes.

State of the art

The ROI vocabulary is converging on cost per successful task. OpenAI's CFO proposes it as a core scorecard metric, and Anthropic tells buyers to pick models on cost per task, settled by their own evals rather than a leaderboard. Proving ROI means attributing spend and outcome to the same unit of work.

Attribution tooling now reaches that unit. Open-source meters attribute tokens to a pull request or a coding agent. Vendor consoles, self-hosted gateways, and platform governance hubs track spend per user and project and surface untagged spend, the gap that breaks chargeback.

The cost side has hidden traps. Per-token savings can vanish in total tokens: quantized reasoning models emit more of them. Measured splits show how much spend buys nothing: only about 7% of agent turns needed a frontier model, and dropping a central orchestrator cut multi-agent cost about half.

The outcome side is still mostly vendor case studies. Reported numbers include a 21% engineering productivity lift and a 250% conversion lift with 40 hours saved per rep. Each is a single, vendor-published customer figure.

The counter-example is the most useful data point. A frontier coding-model rollout to about 3,500 engineers raised total coding spend about 60%, because the model helps on complex work but not the medium- and low-complexity majority. The fix was a budget tier steering the model to tasks where it pays off: cost-per-task attribution, applied after the fact.

The open problem is independent, per-task instrumentation on the outcome side. Spend is now measurable per task; value delivered per task mostly is not.

Why it matters for platform engineers

Platform engineers cannot justify AI budgets on vague productivity claims. They need instrumentation that tracks cost per task, measures outcomes against the labor they replace, and stops token runaway.

When evaluating a model downshift, routing policy, or quantization, cost it on total tokens consumed in the trace, not the sticker price per token. Roll out expensive models by task tier, with attribution in place first, rather than blanket deployment. See cost controls and agent cost.

Databricks' Governance Hub layers an AI-specific view on its account-wide cost dashboards. It tracks token consumption and model activity through Unity AI Gateway, flags per-user spend against budget thresholds, and surfaces untagged spend.

Converging on cost per successful task as the ROI metric

2 entries · latest Jul 26, 2026

Finance and model vendors now frame ROI and model choice as cost per successful task, settled by workload-specific evals rather than per-token price or leaderboards.

Jul 26, 2026·1 source

Anthropic tells buyers to pick models on cost per task, settled by their own evals

Anthropic's model-selection guide tells buyers to compare model classes on cost per task, not cost per token, then settle the choice with evals built for their own workload rather than a leaderboard score.

It folds model selection into the ROI calculation. A cheaper per-token model that needs more tokens or retries can cost more per task, and only a workload-specific eval shows which way it goes.

Sarah Friar, OpenAI's CFO, proposed a practical AI scorecard built on four measures: useful work delivered, cost per successful task, dependability, and return on compute.

It is the per-task attribution engineers argue for, pushed by a finance function. That suggests cost per successful task is becoming the shared ROI vocabulary, not one platform team's convention. It also arrives from a vendor that benefits from compute spend, so treat it as a framing, not a neutral standard.

Databricks' frontier coding-model rollout raised total coding spend ~60%

Databricks reports that rolling out a frontier coding model (Astra, per the newsletter headline) to roughly 3,500 engineers raised total coding spend by about 60%, despite the model's reputation for token efficiency. The model "unambiguously" helps on complex, long-horizon tasks but "may not materially improve medium/low-complexity coding," the bulk of daily work.

Databricks responded with a dedicated budget tier that steers the model toward tasks where it pays off. The figure reached the public secondhand, via an executive's post quoted in a newsletter, so treat it as directional, not audited.

Jul 21, 2026·1 source

Near-free code generation changes which automations are worth building at all

Simon Willison collects anecdotes of people using coding agents to reverse-engineer undocumented home-device APIs and automate them. Before agents this was possible but rarely worth the maintenance risk. When writing the automation is nearly free, so is throwing it away and rewriting it when the API changes.

The ROI shift is not only a lower per-task bill. It removes the cost that used to gate the work, so the set of things worth building grows.
